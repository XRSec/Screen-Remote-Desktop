## 图片理解任务路由（最高优先级）

当前 autoresearch 会话使用的模型不具备可靠的图片理解能力。遇到以下任一情况时，不得凭文件名、尺寸、源码或主观猜测替代视觉检查：

- 判断截图中的卡顿、布局、主题、间距、裁切、缩略图质量或视觉回归。
- 比较改动前后应用窗口截图。
- 阅读图片内容、识别 UI 状态或分析图像解码结果。
- 任何验收条件明确要求“看图”“截图检查”或图片理解。

必须执行以下路由：

1. 暂停当前需要图片判断的实验，不得继续 keep。
2. 开启一个**新的独立会话**，模型明确选择 `CPA/gemini-3.6-flash-high`。
3. 新会话只负责图片理解和视觉验收，不接管 autoresearch、不得自行修改产品代码、不得运行新的 autoresearch 循环。
4. 向新会话提供：待检查图片的准确路径、对应产品页面/状态、需要回答的具体问题、明暗主题与紧凑/宽布局要求，以及相关提交或 diff 范围。
5. 新会话输出结构化结论：观察事实、问题位置、严重程度、是否阻塞 keep、无法确认项。不要让它仅给笼统审美意见。
6. 当前 autoresearch 会话收到视觉结论后，仍需自行结合代码和运行时数据决定 keep/discard；Gemini 会话只提供视觉证据，不拥有最终决策权。

如果无法成功创建 `CPA/gemini-3.6-flash-high` 新会话或图片路径不可读，应将视觉验收标记为 blocked，并停止依赖图片的轮次；禁止使用当前模型假装完成图片理解。

建议的新会话启动提示：

```text
你是 Screen Remote macOS 的只读图片理解与视觉验收会话。当前模型必须是 CPA/gemini-3.6-flash-high。只检查提供的准确图片路径和指定 UI 问题；不要运行 autoresearch，不要修改代码，不要提交。请分别报告观察事实、问题位置、严重程度、是否阻塞 keep、无法确认项，并检查明暗主题及紧凑/宽布局要求（如果素材覆盖）。
```

## 下一轮锁定指令

当前不要继续对 Messages、Notifications、Photos 或其他页面做“发现重复 computed property → 局部 `let` 复用 → Python 代理减半”的同类实验。

下一轮只能二选一：

1. **修复 Apps 实验证据**：建立直接执行产品 Swift 过滤逻辑/同一提取纯函数的 harness，使用现实规模与压力规模重复验证 `4e1dbed`；本轮原则上不再修改产品行为。
2. **Photos 只读测量调查**：先量化当前网格是否拉取原图、请求字节、像素尺寸、缓存与解码路径；没有证据前不实现 helper 缩略图。

如果上述两项都暂时无法建立可信测量，记录 blocked 并停止本轮，不得改选一个更容易归零或天然减半的微型目标。

## 当前判断

自基线 `594b662` 以来，autoresearch 已保留 41 个提交，累计约 952 行新增、119 行删除。产出中包含有价值的状态表达和共享组件修正，但最近明显退化为连续寻找单点 VoiceOver label/value、header trait、单复数和文案正则缺口。

这种模式存在三个问题：

1. 与用户当前最关心的“整体 UI 卡顿”不一致。
2. 静态正则计数天然容易得到 `N → 0`，不能证明用户体验真的改善。
3. 高频小提交持续增加 SwiftUI modifier、格式化和本地化表面积，却没有运行时性能基线或人工 UI 验收。

因此立即停止“为了下一轮而寻找下一个微型缺口”的循环，切换到性能证据驱动模式。

## 强制暂停项

未经监督会话明确批准，不得再选择或 keep 以下类型：

- 单个控件新增 `accessibilityLabel` / `accessibilityValue`。
- 单个视图新增 `.isHeader`、`.combine`、`.ignore` 或命名动作。
- 单复数、计数摘要、空状态标题、提示文案的微调。
- 仅把硬编码字体、间距、圆角替换为 token。
- 仅依据源码正则、字符串存在性或行数计数归零的实验。
- 没有用户可感知性能假设的视觉装饰或结构整理。
- 对同一页面继续做“再补一个语义”的扫尾。

共享组件中的高影响无障碍缺陷只有在能证明覆盖面、无重复朗读风险并经监督批准后才可恢复。

### `4e1dbed` Apps 单次 body 复用过滤结果

产品改动“同一次 `appsContent` 求值复用 `filteredManagedApps`”结构上合理且风险较低，但当前性能结论**不合格，标记为 provisional**：

- `.auto/measure.sh` 用 Python 重写了一份近似过滤算法，没有执行 Swift 产品代码。
- benchmark 通过搜索源码字符串决定 `passes=1/2`，再主动调用 Python `filter_apps()` 一次或两次；约 48.5% 改善是测量器构造出来的预期结果，不是对 App 或 Swift 实现的观测。
- 30,000 个应用远高于典型设备规模，未同时报告 200、500、2,000 等现实规模。
- 首次 crash 以 metric `0` 写入，导致框架显示 baseline 为 0 和 `+Infinity%`，说明本段实验状态已被污染。
- 只运行一次有效基线和一次候选，不满足监督规则要求的重复基线/候选。

处置：

1. 不自动回退产品改动，但不得宣称它已经证明 UI 提速 48.5%。
2. 下一轮不得继续寻找新的重复 `filter` 并照搬同类 Python benchmark。
3. 必须先建立直接执行 Swift 过滤逻辑或可提取纯函数的最窄 harness；至少覆盖现实规模与压力规模，并分别重复测量。
4. 若无法直接测产品逻辑，应把该提交归类为“结构去重、性能收益未证实”，然后转向证据更强的 Photos 字节量/像素尺寸调查。
5. crash 写入错误 baseline 后，必须重新 `init_experiment` 或使用干净 segment 建立有效 baseline；任何显示 `Baseline 0`、`Infinity%` 的段都不得作为 keep 证据。

## 下一阶段唯一优先目标

**降低用户可感知的 UI 卡顿。**

优先调查以下高概率路径，按顺序进行：

### P0：Photos 网格原图拉取与解码

假设：Photos 网格预览直接拉取或解码完整原图，造成网络传输、内存峰值、图片解码和主线程更新压力。

需要先回答：

- 单次刷新拉取多少文件、多少总字节？
- 网格卡片是否请求原图而非受控尺寸缩略图？
- 解码是否发生在主线程？
- 滚动或重新筛选时是否重复请求/解码？
- 是否已有内存/磁盘缓存以及稳定 cache key？

候选方向：复用已部署 dadb helper 生成受控尺寸缩略图；限定像素尺寸；后台解码；去重并缓存 in-flight 请求。不得引入第二个 helper JAR 或远程路径。

### P1：列表/网格 body 中重复计算

重点审计 Apps、Photos、Notifications、Messages、DeviceUtilities：

- `body` 或多处 computed property 是否反复 `filter` / `sorted` / 格式化？
- 同一搜索结果是否为了标题、空状态、ForEach、选择同步重复遍历？
- `DateFormatter`、`ByteCountFormatter`、Attributed/Text 分段是否在每次重绘重建？
- `ForEach` identity 是否稳定？
- 状态变化是否导致整页而非局部刷新？

只优化经过测量确认的热点，不因看到 `filter` 就机械缓存。

### P2：高频状态更新和隐式动画

重点审计 scrcpy ScreenTile、侧栏 session 状态、电量/FPS/码率：

- 高频媒体或会话状态是否发布到过大的 `ObservableObject`？
- 是否导致 RootView、Sidebar 或整个 tile hierarchy 重算？
- 是否对高频值附带隐式动画、overlay 或昂贵字符串格式化？
- 可否缩小观察范围、节流仅展示的数据或拆分等价视图状态？

不得改变 scrcpy、ADB 或窗口生命周期语义。

### P3：累积 41 个 keep 提交的回归审计

在新增性能改动前或并行只读审计以下风险：

- Apps 搜索高亮的 `matchedRanges.sorted` 与多段 `Text` 是否对大量卡片造成明显成本。
- DeviceUtilities 每个 section 中 `actions.filter` 是否重复；通常规模小，除非测量证明，否则不要过度优化。
- 新增 accessibility summary 是否在高频更新路径重复本地化/格式化。
- 折叠侧栏状态 overlay、ScreenTile metrics、搜索匹配计数是否扩大无关刷新范围。

审计结论可以是“不是瓶颈”；不要为了得到提交而强行修改。

## 性能实验最低验收门槛

每个 keep 必须同时具备：

1. **明确场景**：设备/模拟数据规模、页面、用户操作和测量区间。
2. **可复现基线**：至少两次；噪声较大时增加重复次数并报告中位数。
3. **候选对比**：使用相同输入、相同构建方式、相同操作路径。
4. **主指标改善**：运行时指标，而不是源码字符串计数。
5. **正确性守卫**：结果数量、排序、选择、错误处理和业务行为不变。
6. **最窄编译验证**：候选证明有效后执行；基线阶段不反复完整构建。
7. **风险说明**：内存换时间、缓存失效、并发取消、设备数据边界等。

可接受指标示例：

- 直接调用产品 Swift 代码或从产品中提取的同一纯函数，测量相同数据下过滤/排序/摘要生成的 wall time 或中位数。
- 缩略图总传输字节数、最大解码像素、峰值驻留图片字节。
- 单次操作触发的刷新/加载次数。
- 可控 harness 中主线程执行时间或关键函数耗时。
- Instruments/日志证据中的重绘、CPU 或分配变化（能够稳定复现时）。

不可作为唯一 keep 依据：

- 用 Python/JavaScript 重新实现一份算法，然后根据源码字符串选择执行次数的代理 benchmark。
- benchmark 不执行产品代码，却把结果描述为 App 或 SwiftUI 的实际耗时改善。
- 只使用极端合成规模，不报告现实数据规模。
- 单次基线与单次候选的偶然对比。
- 被 crash 的 `metric=0` 污染后产生的 `Infinity%` 或错误 current best。
- `grep`/正则匹配数。
- 新增某个 modifier 后 gap 归零。
- 文件行数减少。
- 编译成功。
- 主观声称“更原生”“更清晰”“更流畅”。

## 迭代节奏

- 一次只调查一个性能路径。
- 先测量，再修改；无法测量则先建立有界 harness。
- harness 必须尽可能直接执行产品代码；若因 SwiftUI 私有 computed property 无法调用，可先做最小的纯函数提取实验，但提取本身不得预设性能改善。
- 数据规模至少包含一个现实档和一个压力档；不得只用 30k 条目制造显著数字。
- 有效基线和候选各至少重复两次完整 benchmark，报告中位数与离散程度；不是只在一次脚本内部循环，然后各运行一次。
- 最多连续两轮测量基础设施；仍无法得到可信数据时记录 blocked 并换方向。
- 不要每 1–2 分钟制造一个提交。
- 每完成一个 keep，下一轮先复核上一轮是否存在性能、布局、双语或 macOS 11 回归，再选择新目标。
- 每 5 个 keep 必须暂停自动新增，输出一次监督摘要：收益、测量可信度、累积复杂度、建议保留/回退项。
